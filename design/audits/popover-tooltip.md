# HIG audit: popover and tooltip

Source: [HIG Popovers](https://developer.apple.com/design/human-interface-guidelines/popovers), read 2026-11-22 (no change log on the page), and [HIG Offering help](https://developer.apple.com/design/human-interface-guidelines/offering-help), read 2026-11-22 (change log: December 5, 2023). Only the tooltip (help tag) part of Offering help is audited; its tips guidance (TipKit, inline and hint tips) is out of scope. Code: `src/components/popover/`, `src/components/tooltip/`, `src/behaviors/anchored.ts`, `src/behaviors/dismiss.ts`, `src/behaviors/position.ts`, `hig/rules/popovers.yaml`, `hig/rules/offering-help.yaml`.

Each guideline is either **library** (the component decides it) or **usage** (the app author decides it, so it belongs in the docs). Verdicts: **met**, **gap**, **deviation** (deliberate, with a reason), or **needs eyes** (a visual judgement for the maintainer). Rows marked "not stated on the HIG page" are platform behavior the pages imply; they are checked against native controls and the web platform, not against Apple's text. Native behavior that was not looked up is marked not verified. Nothing was run for this audit: the e2e tests cited were read, not executed.

### Usage guidelines (for `docs/components.md`, not the component)

- Use a popover for a few related tasks or a small amount of information, not for a large form or a long flow (popovers/1).
- Prefer a popover over a sidebar or panel when the content is needed only briefly.
- Put a Done or Cancel button in the panel only where it clarifies whether the work is kept (popovers/6).
- Save the person's work when the popover closes on its own (`purr-toggle` with `detail.open` false); discard it only on an explicit Cancel (popovers/7). The library closes on an outside press and when focus leaves, so the app must expect both.
- Close the popover yourself after a single selection (`hide()`); leave it open when several selections are possible.
- Do not put another popover inside a popover, and open only one at a time from script (popovers/8).
- Do not use a popover for a warning; use an alert (popovers/11).
- Give every popover a `label`; the panel is a dialog and fails axe without a name (`popover.e2e.ts:152`).
- In compact views, such as a phone-width page, use a sheet instead of a popover (HIG iOS and iPadOS guidance). The library has no such fallback.
- In help text, name the task or selection, not the word "popover".

### Usage guidelines (for `docs/components.md`, not the component)

- Describe only the control the tooltip belongs to, not nearby controls or a larger task (offering-help/2).
- Explain the action the control starts, often beginning with a verb ("Restore default settings"); do not repeat the control's name (offering-help/3).
- Keep the text to 60 to 75 characters as a sentence fragment without articles; if more is needed, simplify the interface (offering-help/4).
- Use sentence case and omit closing punctuation unless the app's style needs it (offering-help/5).
- Change `text` with the control's state when its meaning changes (offering-help/6).
- Name the specific action a standard control performs; do not explain the control itself (offering-help/7).
- A tooltip is a description, not a name: an icon-only control still needs its own accessible name.
- Do not put essential information or interactive content in a tooltip; touch users never see it.
- Call it a help tag in user documentation (HIG wording).

## Findings outside HIG

- A popover without a `label` renders with no accessible name and is caught only by a test (`popover.e2e.ts:152`), not at runtime (`popover.ts:168` omits `aria-label` when `label` is empty).
- The tooltip's delay is a fixed 560ms in CSS (`tooltip.css.ts:14`), not a token, so an app cannot change it without overriding `transition-delay` on the host.
- Not verified: a tooltip on a disabled control, nested popovers and Escape handling, and an alert opened over a popover. No test or story covers them.
