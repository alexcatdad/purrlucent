# HIG audit: menu (menu button, context menu, submenu)

Source: [HIG Menus](https://developer.apple.com/design/human-interface-guidelines/menus), read 2026-11-22 (change log: June 8, 2026), and [HIG Context menus](https://developer.apple.com/design/human-interface-guidelines/context-menus), read 2026-11-22 (change log: December 5, 2023). Code: `src/components/menu/`, `src/behaviors/dismiss.ts`, `src/behaviors/position.ts`, `src/components/select/match.ts`, `hig/rules/menus.yaml`, `hig/rules/context-menus.yaml`.

Each guideline is either **library** (the component decides it) or **usage** (the app author decides it, so it belongs in the docs). Verdicts: **met**, **gap**, **deviation** (deliberate, with a reason), or **needs eyes** (a visual judgement for the maintainer). Rows marked "not stated on the HIG pages" are platform behavior the pages imply; they are checked against the web platform and the WAI-ARIA menu pattern, not against Apple's text, and no native macOS menu was run for this audit.

One element, `purr-menu`, serves all three uses: from a trigger in the `trigger` slot (menu button), at a point through `showAt` (context menu), and nested in a `purr-menu-item`'s `submenu` slot (submenu). Rows apply to all three unless they say otherwise. The pop-up button and pull-down button pages are separate pages and were not read for this audit; the stories draw the trigger as a `purr-button` with a chevron.

## Usage guidelines (for `docs/components.md`, not the component)

Menus

- Label an item that starts an action with a verb or verb phrase, short, without articles; don't pad a label (menus/1).
- End the label with an ellipsis (…) when the action needs more input before it completes, as the `Find…` item in the stories does (menus/3).
- Show a shortcut in `detail` only for a real key binding, and bind the key in the app: the component only displays the text (menus/4).
- Use item icons sparingly, and only where one clearly represents the item. Give every item in a group an icon, or none: the component does not enforce it, and a row without an icon lines up differently from one with an icon (menus/5).
- Put important or frequently used items first, keep related commands in one group even when they differ in importance, and divide groups with `purr-menu-separator` (menus/6).
- Keep a menu short. Split it, or use a submenu, unless the content is user-defined or generated, such as history, where scrolling is fine (menus/7).
- Use submenus sparingly, one level deep, with about five items at most. Name the submenu row with the term its items share, such as "Sort By". Prefer a submenu to indenting items. The component allows deeper nesting and does not limit it (menus/8).
- For one attribute that turns on and off, change the label (Show Map, Hide Map) or use a checkmark; add a verb if a changing label is unclear (Turn HDR On); consider a Plain item that clears several checked attributes (menus/9).
- A menu that opens from a pull-down or pop-up button belongs with those pages (pull-down-buttons, pop-up-buttons); see their rules.

Context menus

- Open the menu from a `contextmenu` event that calls `preventDefault()` and `showAt(event.clientX, event.clientY)`, as the `ContextMenu` story does. The component does not listen for the event itself. For touch and keyboard (a long press, the context-menu key), whether the browser fires `contextmenu` was not checked; test it in the app (unverified).
- Hold only the commands most relevant to the item, few in number, and support a context menu consistently across the app (context-menus/2, context-menus/3).
- Every command in a context menu must also be reachable in the main interface, such as a toolbar or menu bar (context-menus/3).
- Leave out items that do not apply instead of using `disabled`. The page's one exception is Cut, Copy and Paste on macOS, which may appear unavailable. The `ContextMenu` story shows a disabled "Compress" and so does not follow this (context-menus/4).
- Don't put keyboard shortcuts in a context menu's items; put them in the main menus (context-menus/5).
- Use about three groups at most (context-menus/6).
- List destructive items last and mark them with `destructive` (context-menus/8).
- When the menu opens above the point, reverse the order of the items yourself (see the gap above) (context-menus/7).
- Give the menu a visible title, with a `purr-menu-label` as the first child, only when it clarifies the effect, such as the number of selected items. `label` names the menu for assistive technology and draws nothing (context-menus/9).
- On iOS and iPadOS, don't offer both a context menu and an edit menu on the same item.

## Findings outside HIG

- The `ContextMenu` story contradicts the Context menus page: it shows a disabled item (`Compress`, `menu.stories.ts:201`) in a context menu. The page says to hide unavailable items there.
- A `purr-menu-label` is `role="presentation"` (`menu.ts:154`) and the radio items below it are not in a `role="group"`, so a screen reader does not hear "Sort By" with the radio group. The aria snapshot records it as plain text (`menu.e2e.ts:45`). The WAI-ARIA menu pattern uses `role="group"` with a name for this. Not stated on the HIG pages.
- Menu items are `purr-menu-item` elements, not native `button` or `a`, so an item cannot be a link (a menu item that navigates) and has no form behavior. Not stated on the HIG pages.
- The menu follows page scroll and resize by repositioning (`menu.ts:463-464`); native menus usually close instead. Not stated on the HIG pages, and not checked against a native menu.
