# HIG audit: button

Source: [HIG Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons), read 2026-11-22 (change log: December 16, 2025). Code: `src/components/button/`, `src/behaviors/pressable.ts`, `src/behaviors/interaction.css.ts`, `hig/rules/buttons.yaml`.

Each guideline is either **library** (the component decides it) or **usage** (the app author decides it, so it belongs in the docs). Verdicts: **met**, **gap**, **deviation** (deliberate, with a reason), or **needs eyes** (a visual judgement for the maintainer). The page covers iOS, macOS, visionOS and watchOS; only guidance that applies to a web push button is audited, and the rest is listed under usage or findings.

## Usage guidelines (for `docs/components.md`, not the component)

- Keep space around each button so it stands apart from nearby content and controls (buttons/1).
- Use one or two prominent buttons per view; give the most likely action the primary variant and the rest quieter variants (buttons/3, buttons/8).
- Give buttons of equal weight the same size; show the preferred choice by variant, not size (buttons/4).
- Never make a destructive action the primary button, even when it is the most likely one (buttons/9).
- Write a few words, in title-style capitalization, starting with a verb, for example "Add to Cart"; use a familiar icon when it is clearer than text; an icon-only button needs an `aria-label`.
- End the label with an ellipsis when the button opens another window, view or app (buttons/10).
- Avoid a label color close to colorful content behind the button (buttons/5).
- For a help button, use no more than one per window, in a lower corner and without introductory text; the library has no help button component (macOS).
- Use icon and image buttons in a view, not in a toolbar or status bar; a toolbar needs its own component (macOS).
- Add a tooltip to an icon-only button that explains it; the page says macOS and visionOS show one on hover. Not part of this library.
- For a delayed action, show your own feedback until the library has a busy state (iOS and iPadOS).
- Spring loading, the visionOS shapes and sounds, and the watchOS full-width layout are not web concerns and are not audited.

## Findings outside HIG

- `purr-button` is a custom element with `role="button"` (`button.ts:79-82`), not a native `button`. It submits and resets forms (`button.ts:71-76`), but it has no `name` or `value`, so it cannot report which submit button was used. Not verified against a native button beyond the code read.
- A toggle reuses the button (`docs/components.md:724`), so any button change also changes the toggle.
