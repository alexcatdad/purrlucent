# HIG audit: progress and spinner

Source: [HIG Progress indicators](https://developer.apple.com/design/human-interface-guidelines/progress-indicators), read 2026-11-22 (change log: September 12, 2023). Code: `src/components/progress/`, `src/components/spinner/`, `hig/rules/progress-indicators.yaml`.

One HIG page covers both components: `purr-progress` is the progress bar, `purr-spinner` is the activity indicator (spinner). Each guideline is either **library** (the component decides it) or **usage** (the app author decides it, so it belongs in the docs). Verdicts: **met**, **gap**, **deviation** (deliberate, with a reason), or **needs eyes** (a visual judgement for the maintainer). Rows marked "not stated on the HIG page" are platform behavior the page implies.

### Usage guidelines (for `docs/components.md`, not the component)

- Prefer a determinate bar when the extent is known; use indeterminate only when it is not (progress-indicators/1, /2).
- Report progress evenly and never send a lower value than before; an even pace feels trustworthy, a jump from 90% to done after minutes feels deceptive (progress-indicators/5).
- If work stalls, say so and offer a way forward; a still bar reads as a frozen app.
- Switch to determinate as soon as the extent is known by setting `value`.
- Add a visible description only when it helps; make it short and specific, not "Loading" or "Authenticating" (progress-indicators/7). `label` is the accessible name, so make it specific too.
- Show the indicator in a consistent place across the app (progress-indicators/8).
- Offer Cancel when stopping is safe. When stopping loses progress, offer Pause as well and confirm Cancel with an alert (progress-indicators/9).
- Show the indicator only while the operation runs and remove it when it ends (progress-indicators/11). `hidden` works on the host.

### Usage guidelines (for `docs/components.md`, not the component)

- Use a spinner for background work or when space is tight, such as next to a control; use a bar when the extent is known (progress-indicators/10).
- Don't add a visible label to a spinner; the action that started the work usually explains it. Still pass `label` so it has an accessible name (`docs/components.md:629`).
- Never swap a spinner for a progress bar, or the reverse, in the same place; the shapes differ in size and the change disrupts the layout (progress-indicators/6).
- Remove the spinner when the work ends (progress-indicators/11).
- Show it in a consistent place; offer Cancel when stopping is safe (progress-indicators/8, /9).
- Inside a button, a spinner is not built in; button progress state is out of scope for now.

## Findings outside HIG

- Both components take their only text from `label`, so the app localizes it and there is no built-in English default. A missing `label` is caught by axe in tests only, not at runtime (`progress.e2e.ts:153`, `spinner.e2e.ts:103`).
- `role="progressbar"` is set in `connectedCallback` on the host (`progress.ts:35`, `spinner.ts:40`); an app that sets its own `role` on the element is overwritten only at connect time.
- Rules progress-indicators/5 to /11 are rubric checks with no test; the usage lists above are where they are documented.

## Source of truth

`src/tokens/tokens.css` is the source of truth for sizes, radii, spacing, durations and colors (decided 2026-11-22). `design/visual-spec.md` has no progress or spinner section and is superseded where it differs from the tokens.
