# HIG audit: toolbar and banner

Source: [HIG Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars), read 2026-11-22 (change log: December 16, 2025). For the banner, HIG has no banner page; see the banner section for which pages were used: [HIG Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts), read 2026-11-22 (change log: February 2, 2024), and [HIG Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications), read 2026-11-22 (change log: October 24, 2023). Code: `src/components/toolbar/`, `src/components/banner/`, `src/behaviors/roving-focus.ts`, `src/surfaces/surfaces.css.ts`, `hig/rules/toolbars.yaml`, `hig/rules/alerts.yaml`.

Each guideline is either **library** (the component decides it) or **usage** (the app author decides it, so it belongs in the docs). Verdicts: **met**, **gap**, **deviation** (deliberate, with a reason), or **needs eyes** (a visual judgement for the maintainer). Rows marked "not stated on the HIG page" are platform behavior the pages imply; they are checked against native controls and the web platform, not against Apple's text. Nothing was run for this audit: no tests, no Storybook, no browser against the library; the verdicts come from reading the source, stories and e2e files.

## toolbar

### Usage guidelines (for `docs/components.md`, not the component)

- Choose items deliberately; put less important actions in a More menu rather than crowding the bar, and avoid layouts that overflow by default (toolbars/1). The library has no overflow menu, so the author decides.
- Title each window or view with a concise name, under 15 characters, never the app name (toolbars/5). Leave the title empty when it would be redundant.
- Use the standard back and close symbols, with an accessible name, and no "Back" or "Close" text (toolbars/6).
- Give every icon-only item an `aria-label`; prefer a simple symbol, and use text for an action such as Edit that a symbol cannot carry (toolbars/7).
- Group items by function and frequency; put navigation and critical actions (Done, Close, Save) in their own groups; aim for at most three groups (toolbars/10).
- Keep text-labeled actions out of a symbol group, and separate adjacent text buttons (toolbars/11).
- Mark one key action `variant="primary"` and put it last (toolbars/8).
- Set `scrolled` while content scrolls under the bar.
- Avoid a bar background or tinted controls, and avoid label colors close to the content colors behind the bar (toolbars/2, toolbars/3).
- macOS guidance: every toolbar item is also a command in the menu bar, because the toolbar can be hidden or customized. On the web, make each item available another way (menu, shortcut).
- Keep the toolbar consistent across platforms and views.

## banner

The banner is the library's inline notice: an icon, a title, a message, optional actions and a close button, rendered in the page flow (`banner.css.ts:14-23`, no positioning).

### Which HIG guidance applies

HIG has no banner page. Two pages were read, and each applies in part:

- **Alerts** applies to the placement question. "Avoid using an alert merely to provide information... prefer finding an alternative way to communicate it within the relevant context" and the startup advice ("show cached or placeholder data and a nonintrusive label") describe exactly what an inline banner is for. A banner is not an alert: it is not modal and takes no focus. So the alert rules about buttons, Cancel, OK, Escape and the three-button limit are not applied, except where the banner has a destructive tone or actions (noted per row).
- **Notifications** applies to the content and actions. The page defines a "banner" as one notification style, shown by the system on a Lock Screen or desktop, outside the app. The library banner is an in-app surface, so the system rules (consent, badges, sound, Watch short and long looks, foreground handling) do not apply. The content guidance (concise, informative text; title that gives context; up to four actions with short title-case verbs; nondestructive actions preferred; no duplicate notices; do not use a notification for an error) is applied as the nearest HIG text for a short message with actions.

Both choices are a reading by this audit, not something HIG states for inline notices.

### Usage guidelines (for `docs/components.md`, not the component)

- Use a banner for information shown in context, such as a connection problem or an available update. Do not use an alert for information that needs no decision (alerts/2), and do not show an alert at launch (alerts/4).
- Keep the title and message concise. Make the title say what happened; never just "Error" (alerts/5, in spirit). Use sentence case for the message and no ending punctuation on a fragment title.
- Show one banner per situation. Replace or update an open one instead of adding another (Notifications: avoid multiple notices for the same thing).
- Give at most four actions, each a short verb phrase naming the result. Prefer nondestructive actions, and do not add an action that merely goes where the banner's own text already leads (Notifications).
- Do not tell people to perform a task inside the app in the message; offer it as an action.
- Leave the icon slot empty to get the tone's own icon. When you slot an `svg`, give it `aria-hidden="true"` and pick a different icon for each tone so the tone is not carried by color alone (not stated on the HIG pages).
- Do not put sensitive or private information in a banner (Notifications).
- Decide whether the banner stays until closed or is removed by the app; the library never closes it by itself.
- For an error that needs a decision or blocks the task, use a dialog instead (alerts/1, alerts/3).

## Findings outside HIG

- **toolbar:** `#onSlotChange` passes only direct children to `prominentIssue` (`toolbar.ts:146-153`, `190-194`), so a `variant="primary"` button inside a `purr-toolbar-group` escapes both the "at most one" and the "last" check, and it does not get the trailing margin (`toolbar.css.ts:58-60` uses `::slotted`).
- **toolbar:** the `prominent` and label warnings are `console.warn` only (`toolbar.ts:185`, `194`); nothing stops an invalid toolbar from rendering.
- **toolbar:** the separator's negative margin cancels the toolbar gap with `calc((gap + 1px) / -2)` (`toolbar.css.ts:93`), which is correct only when the separator sits directly in the bar; inside a group the group's own rule overrides it (`toolbar.css.ts:175-180`). Not verified in a browser.
- **banner:** the default `close-label` is "Dismiss" (`banner.ts:45`); the attribute localizes it, which is the approach `design/decisions.md` item 6 adopts for every built-in string.
- **banner:** the `tone` name "destructive" names an error or problem state, not a destructive action (`banner.ts:13`, `banner.css.ts:35-38`); HIG uses "destructive" for an action that destroys data (alerts/8). A name such as `error` would describe the state, but renaming is the maintainer's call, and there is no warning or success tone.
- **banner:** `willUpdate` keeps an author role forever, including after `tone` changes (`banner.ts:47-53`, test at `banner.e2e.ts:85-92`); intended.

## Source of truth

`src/tokens/tokens.css` is the source of truth for sizes, radii, spacing, colors and durations (decided 2026-11-22). `design/visual-spec.md` has a "Toolbar bar" section (`visual-spec.md:285-306`) and lists toolbar zones and the overflow menu as out of scope (`visual-spec.md:9`); it has no banner section. It is superseded where it differs from the tokens, so those "out of scope" notes are not a reason for the toolbar gaps above.
